## 一、时间轴与讲稿要点

### 0:00–0:40　问题（讲痛点，不要念功能列表）

> 开源社区的新人流失，大多发生在「想参与但不知道从哪下手」的头一个小时。
> 我们调研魔搭社区发现三个断点：**新手不知道路线**、**选模型靠碰运气**、
> **想贡献代码却看不懂 Issue**。现有的文档是「人找知识」，我们想反过来做「知识找人」——
> 把一个懂社区规范的 AI 助手，放进新人动手前的每个决策点。

### 0:40–1:00　方案一句话 + 打开页面

> 所以我们做了 ModelScope AI Copilot：五个场景覆盖「入门 → 选模型 → 做贡献 → 诊断项目」全链路。
> 前端 React，后端 FastAPI，大模型 DeepSeek，**所有回答都基于真实数据与社区官方规范**。

（切到首页停留 2 秒即可，别恋战——美观度评委自己会看。）

### 1:00–2:00　演示 ①：新手导航 + 结构化输出

点「新手导航」卡 → 点「✨ 前端新手入门」。

> 看，它不是泛泛而谈，而是按周给出**带入口、带耗时、带完成标准的任务表**——
> 这是我们把魔搭官方术语和社区规则写进 System Prompt 的结果，
> 模型输出被约束成固定结构，而不是闲聊。

### 2:00–3:00　演示 ②：模型推荐 + 多轮追问（顺带秀流式）

点「模型推荐」→ 问：「我要做中文语音识别，推荐一个模型」。
回答出来后**马上追问**：「那第二个呢？它的延迟什么水平？」

> 注意两点：第一，回答是**逐字流式**出现的，首字 1 秒左右——
> 我们关掉了推理模型的思维链，把单轮响应从 50 秒压到 4 秒；
> 第二，它能理解「第二个」指上文哪个模型，**多轮上下文是完整实现的**，
> 这是对话式助手和套壳问答最本质的区别。

### 3:00–4:00　演示 ③：健康度诊断（最硬的创新点，留足时间）

点「健康度诊断」→ 点「✨ ms-swift 项目诊断」。

> 这是评委最该关注的功能：**它的每个数字都是真的**。
> 系统先实时抓取 GitHub REST API——Star 数、近 30 天提交、Issue 48 小时响应率、
> 文档信号、Good First Issue 数量——再让模型做**归因分析和治理建议**，
> 而不是让模型编一份报告。页面上直接标注了数据来源和抓取日期，
> 拿不到的维度它会明说「数据未获取到」，**宁可承认缺失，也不编造指标**。

### 4:00–4:40　创新点总结（对着披露页说，顺便展示合规设计）

切到「AI 披露」版块：

> 总结三个创新点：**一，真实数据驱动的 AI 分析**——模型只负责归因，指标来自实时抓取；
> **二，全链路可观测的服务降级**——流式、非流式、本地知识库三级兜底，
> 每条回答都标注来源和实际模型，降级内容绝不冒充 AI 输出；
> **三，负责任的工程化**——按 IP 限流保护 API 余额、链接协议白名单防注入、
> 独立的 AI 使用披露页。这些不是包装，是能被代码验证的。

### 4:40–5:00　实用性与收尾

> 对社区的价值很直接：新人上手时间从「天」级压到「小时」级，
> 维护者的 Issue 沟通成本下降。下一步我们计划把助手接入魔搭文档站和
> 仓库 Issue 模板，让它在真实的贡献动线上发挥作用。谢谢各位评委。

## 二、评委问答预案（2 分钟）

**Q1：健康度数据真的是抓的？会不会是模型编的？**
> 是实抓的。前端每次诊断都会标注「数据来源：GitHub REST API 实时抓取 + 日期」，
> 评委可以当场提一个新仓库验证；抓取失败时页面会明确写「数据未获取到」，
> 模型只给评估框架并声明这不是真实测评——我们把这个诚实行为做成了产品特性。

**Q2：为什么选 DeepSeek？换模型成本高吗？**
> 模型是环境变量配置的，业务代码不绑定任何厂商。选 DeepSeek 看重性价比和中文能力；
> 而且我们实测了推理开关：这类格式明确的任务型问答关掉思维链，54 秒变 4 秒，质量不掉。

**Q3：和直接问 ChatGPT/豆包有什么区别？**
> 三点：**场景化**——System Prompt 植入了魔搭官方术语、创空间发布规范、CLA 流程，输出是可用的工作产物而非科普；
> **真实数据**——通用聊天机器人不会替你抓 GitHub 指标；
> **工程可用**——限流、降级、来源标注，是可以直接部署进社区的服务，不是一个聊天窗口。

**Q4：API Key 和成本怎么保护？公开演示不怕被刷爆吗？**
> 后端按 IP 滑动窗口限流（默认 12 次/分钟，可配），Key 只存在于服务器环境变量、不进仓库；
> 前端还做了协议白名单，防止 AI 输出里的链接被注入恶意脚本。

**Q5：AI 在你们开发里占了多少？怎么保证质量？**
> 披露页有完整分工表：AI 出初稿（组件/接口/Prompt/文案），人工逐行审查、
> 与官方文档核对、真实场景测试。可以说「AI 写初稿，人对结果负责」。

**Q6：后续怎么落地？**
> 两条路：嵌入魔搭文档站做新手引导；接进仓库 Issue 模板做自动摘要。
> 技术上无障碍——后端是标准 REST/SSE 接口，前端可独立部署。

**Q7（刁钻）：模型答错了、给了过时的社区规则怎么办？**
> 三层缓解：Prompt 里锁定官方术语与文档链接并要求「以官方文档为准」；
> 关键数字不让模型生成，由代码实抓；界面上每条回答都标注来源，
> 用户永远知道自己在看什么。

## 三、应急预案

| 现场状况 | 处置 |
|---|---|
| 页面打不开 / 白屏 | 用 `python3 deploy/serve_like_platform.py` 的本地环境演示（提前跑通一遍） |
| 回答很慢 | 等首字即可（1–2 秒内会出），期间顺势讲流式实现与思维链优化 |
| 徽标显示「本地知识库降级」 | **不要慌，主动讲**：「这正是我们的三级降级设计，AI 不可用时服务不中断，且如实标注」——把故障变成加分项 |
| 健康度显示「数据未获取到」 | 主动解释这是 GitHub 未认证限流（60 次/小时），并强调「我们宁可标注缺失也不编数据」 |
| 被问不会的问题 | 「这个问题我们目前的设计没有覆盖，会后我们验证后补充到披露页」 |

## 四、答辩人提示

1. **不要念代码、不要念 README**，评委看的是「问题真不真、方案硬不硬、演示稳不稳」。
2. 每个场景演示**不要等完整回答输出完**，看到前几行就开始讲，时间才够。
3. 健康度诊断是差异化最强的一环，**时间再紧也要保住这 1 分钟**。
4. 结尾一定落到「可部署、可验证」，呼应实用性维度。
